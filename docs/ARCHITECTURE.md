# Архитектура

Smart Plant OS — распределённая локальная система: **Smart Plant Hub** (ESP32-S3 N16R8) ↔ ESP-NOW ↔ до десяти **Smart Plant Node** (ESP32-C3 Super Mini). Это проектная архитектура: прошивок и стендовых испытаний пока нет. Решения и их статус — в [ADR](adr/README.md); сеть и ESP-NOW — в [NETWORK.md](NETWORK.md).

**Hub определяет политику и координирует. Node проверяет и исполняет.**

```text
браузер / Home Assistant / ИИ (будущее)
        │  REST /api/v1  (JSON, spec/v1)
        ▼
  ┌───────────── Hub, ESP32-S3 ─────────────┐
  │ веб-интерфейс · реестр · привязка        │
  │ история (интерфейс хранилища, microSD)   │
  │ адаптер REST ⇄ SPP                       │
  └───────────────┬─────────────────────────┘
                  │  SPP (CBOR) поверх ESP-NOW
        ┌─────────┴─────────┐
        ▼                   ▼
   Node, ESP32-C3  …   Node, ESP32-C3     (до 10)
   датчик · бак · защита · драйвер насоса
```

## Единица системы: Node

Node — одна ESP32-C3 и одно растение. У него собственные `device_id`, `plant_id`, почвенный датчик, датчик наличия воды, насос, конфигурация и краткий журнал. Замена имени или адреса Wi-Fi не меняет ID. Перенос растения на другую плату — отдельная операция миграции, в которой сохраняется `plant_id`, но меняется `device_id`.

```text
датчики → нормализация и качество → состояние → правило полива → защита → драйвер насоса
                                      ↑                ↑
                                   настройки       команды SPP
                                      ↓                ↓
                                 журнал событий ← результат
```

Слой драйверов зависит от платы. Модель данных, проверки команд и логика решения не зависят от платы и лежат в общих компонентах, которые тестируются на хосте. Обработчик радиоканала не включает GPIO напрямую.

## Разделение ответственности

| Компонент | Отвечает за | Не отвечает за |
|---|---|---|
| Node | измерение, калибровку, локальные правила полива, все защитные ограничения, драйвер насоса, краткий журнал, обмен по SPP | каталог устройств, историю, веб-интерфейс, облачные советы |
| Hub | веб-интерфейс, REST API, реестр и привязку узлов, настройки и политику, агрегирование и хранение истории, диагностику сети, интеграции | решение о запуске насоса, жёсткие пределы узла |
| Веб-приложение | показ измерений и причин решений, настройки через API, подтверждение команды | вычисление фактического объёма, управление GPIO |
| Адаптеры (Home Assistant, ИИ, экспорт) | чтение состояния и истории, предложения изменений | изменение защитных лимитов в обход API и подтверждения пользователя |

Ни Hub, ни веб-интерфейс, ни ИИ, ни Home Assistant не имеют пути к GPIO насоса в обход локального контроллера безопасности Node ([ADR-0001](adr/0001-roles-hub-node.md)).

## REST API и адаптация

Публичный REST API `/api/v1` принадлежит Hub и сохраняет семантику [контракта v1](PROTOCOL.md): `State`, `Config`, `CommandResult`, `EventPage`, `Registry`. Маршруты `/api/v1/nodes/{device_id}/…` обслуживает Hub, собирая ответы из сообщений SPP. Если узел недоступен, Hub отвечает `503 node_offline` и не выдаёт устаревший снимок за текущий. Внутренний обмен описывает отдельный протокол SPP ([ADR-0002](adr/0002-transport-espnow-and-spp.md), [ADR-0003](adr/0003-serialization-cbor.md)); транспорт ESP-NOW подключается за узким интерфейсом и может быть заменён.

## Автономность

Локальная конфигурация Node — источник правил исполнения. Потеря Hub, Wi-Fi, microSD или веб-интерфейса не отключает сохранённые правила и не ослабляет защиту.

- После первоначальной настройки Node продолжает **разрешённый** автоматический полив в пределах сохранённой конфигурации, если проверки достоверности и безопасности пройдены ([WATERING.md](WATERING.md)).
- Если состояние небезопасно или неизвестно, насос не включается.
- Ручная команда полива имеет срок действия; Hub не ставит её в очередь для недоступного узла. Конфигурация может дожидаться связи, команда полива нет.
- После перезагрузки без достоверного календарного времени автополив заблокирован до получения времени от Hub, причина `clock_unset`. Ограниченный автономный полив после перезагрузки не вводится ([ADR-0005](adr/0005-time-and-restart.md)).
- Причины отказов, возникшие без связи, Node сообщает после её восстановления.

## Данные и время

Настройки и калибровка хранятся на Node. Справочник видов — набор советов, а не источник обязательных ограничений. Каждое событие получает на узле последовательный `seq` и `event_id`; Hub запрашивает события после последнего полученного `seq`. Пропуски после переполнения кольцевого журнала обозначаются кодом `cursor_expired`.

Время имеет качество `synced` или `unset`. Монотонный таймер нужен для максимального времени работы насоса и паузы после полива; календарное время нужно для суточного лимита и расписаний. Обрыв связи после успешной синхронизации не сбрасывает монотонные таймеры.

NVS подходит для небольших настроек и калибровки; журнал и прочие данные требуют отдельного бюджета разделов flash. Размеры разделов и интервалы записи не утверждены.

## История и microSD

Долгая история хранится на Hub за узким интерфейсом хранилища ([ADR-0007](adr/0007-history-storage-interface.md)). История не участвует в решении о поливе. Отсутствие или отказ карты не останавливает показания и команды; Hub показывает «история недоступна». Node хранит только короткий журнал и минимальное состояние. Формат экспорта — JSON Lines из объектов `Event`. Файловая реализация, индексы и восстановление после сбоя вынесены в отдельный этап.

## Возможности устройств

Hub не предполагает одинаковый набор датчиков у всех узлов. Устройство объявляет `capabilities`; интерфейс показывает только объявленное. Для MVP обязательны датчик почвы, контроль воды в баке и насос. Температура, влажность воздуха, освещённость, батарея и расход воды — необязательные возможности. Расширение схемы `capabilities` делается только необязательными полями внутри v1 ([PROTOCOL.md](PROTOCOL.md)).

## Сеть и доверие

Node общается с Hub только по ESP-NOW и не имеет HTTP-сервера. Непривязанный Node не принимает команд. Привязка требует физического подтверждения, шифрование канала не заменяет её ([ADR-0004](adr/0004-pairing-and-keys.md), статус «Предложено»). Доступ браузера к Hub описан в [ADR-0009](adr/0009-browser-access-to-hub.md) (статус «Предложено»). Команды получают стабильный `command_id`, чтобы повтор после тайм-аута не вызвал второй полив. Глобального правила полива нет: каждый узел независим.

## Будущие интеграции

Home Assistant получит адаптер к тем же состояниям и командам через Hub. MQTT Discovery потребует постоянных `unique_id`, описания устройства и availability; связь с узлом и исправность его датчика — разные статусы. ИИ может читать состояния и историю, диагностировать, предлагать и объяснять изменения; применение предложений проходит подтверждение пользователя и проверку лимитов на узле.
