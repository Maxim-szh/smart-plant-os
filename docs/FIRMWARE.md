# Основа прошивок 0.1.0 — инженерный профиль

Это код для подготовки и проверки стенда, а не законченная OS. Два проекта ESP-IDF **v5.3.4**: [Node](../firmware/node) для ESP32-C3 Super Mini с предполагаемыми 4 MB flash и [Hub](../firmware/hub) для ESP32-S3 N16R8 с 16 MB flash / 8 MB octal PSRAM. Объём памяти и ревизию нужно проверить на конкретных платах. Сборка не доказывает аппаратную совместимость.

## Как связана вся система

```text
Будущие UI / REST / Home Assistant
             ↓ адаптер команд и данных (ещё не реализован)
Hub: реестр + повторы RPC + восстановление истории + интерфейс storage
             ↓ sp_message_t / ограниченный CBOR / AEAD / ESP-NOW
Node: проверка сообщения → sp_core → сохранение решения → драйвер насоса
                                  ↑                  ↓
              калибровка ← качество измерения    независимый таймер отключения
                                  ↑
                  ADC1 / Capacitive Soil Moisture Sensor v1.2
```

Работающий вход первого профиля — USB-консоль. Она использует тот же `sp_node_dispatch`, что радио. HTTP-сервера, точки доступа и подключения HTML к устройствам здесь ещё нет. Отдельной «упрощённой» логики полива для консоли нет.

| Граница из документации | Код сейчас | Следующий шаг |
|---|---|---|
| Локальная защита Node | `sp_core.c`: состояния, лимиты, калибровка, дедупликация, восстановление | стенд с насосом и измерение времени отключения |
| Сменные драйверы | `sp_board.c`: ADC1, поплавок, активный высокий выход, GPTimer | проверенная схема; затем отдельные драйверы других датчиков |
| SPP и транспорт | `sp_wire.c`, `sp_crypto.c`, `sp_radio.c`: CBOR, AEAD, replay, ESP-NOW | измерить потери/задержки на 1 и 10 устройствах |
| Локальные настройки | NVS safety, атомарный blob; ожидаемая revision | миграции формата при первом изменении layout |
| Реестр Hub | фиксированные 10 записей, online по валидной телеметрии, 15 s | постоянные имена/виды растений и полноценный REST-адаптер |
| История | Node: 32 устойчивых события; Hub: 128 записей RAM, `append/read_after/bounds` | файловый backend, устойчивые курсоры Hub, JSON Lines |
| Привязка | физическая загрузка индивидуальных ключей через USB | пользовательская процедура из ADR-0004 |
| Время | UTC через физическую консоль Hub; монотонные защиты на Node | ввод времени из авторизованного браузера |
| Браузер / публичный API | схемы v1 и правила преобразования SPP; сервер отсутствует | ADR-0009, HTTP auth/TLS, все ответы проверять JSON Schema |
| Home Assistant / NAS / SD | границы команд, идентичности, availability и storage | отдельные адаптеры после проверки MVP |

Последовательность не меняется: сначала ядро и обмен, затем стенд, REST и живой интерфейс, затем интеграции. Нельзя подключать MQTT, NAS или карту в обязательный путь запуска/остановки насоса.

## Владение данными и задачами

Вся изменяемая доменная модель принадлежит одному application task. Wi-Fi callbacks только помещают кадр в очередь из 16 элементов или подтверждают завершение передачи. В них нет GPIO, NVS и криптографии. Переполнение очереди теряет пакет, клиент повторяет запрос с тем же ID. MAC ACK не считается выполненной командой.

Чтение бака — каждые 100 ms, почвы — каждые 500 ms после 2 s прогрева; телеметрия — раз в 3 s. Эти значения — начальные инженерные настройки. Watchdog application task — 5 s с panic/reset. Таймер GPTimer выключает выход в ISR независимо от основного цикла, в том числе во время операций flash; ISR и данные находятся во внутренней памяти. Проверка отсутствия воды в баке всё ещё выполняется основным циклом, её задержку нужно измерить на стенде. Программный таймер не заменяет безопасную электрическую схему.

Для протокола, истории и ядра используются ограниченные структуры и целочисленные единицы. Нет выделений памяти на каждый пакет или измерение. Динамическую память при старте используют SDK и драйверы. Оптимизировать следующие этапы нужно по map-файлу и измерению минимального свободного heap, а не уменьшением количества проверок.

## Что делает профиль датчика v1.2

Это обобщённый профиль аналогового ёмкостного датчика; маркировка v1.2 у разных продавцов не гарантирует одинаковую схему. Напряжение выхода и питание проверяются мультиметром до подключения. Вход не должен превышать допустимое напряжение ADC конкретной платы. Используется ADC1, 12 бит, attenuation 12 dB; ADC2 на C3 не используется ([Espressif, ADC oneshot](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32c3/api-reference/peripherals/adc_oneshot.html)).

1. Медиана девяти чтений подавляет одиночные выбросы. Разброс между вторым и восьмым значением больше 300 отсчётов означает `fault`.
2. Медиана ≤15 или ≥4080 означает `fault`. Ошибка ADC тоже считается ошибкой измерения.
3. EWMA с коэффициентом 1/4 сглаживает значение; вычисление фиксированной точкой Q8. После ошибки фильтр начинает накопление заново.
4. Калибровка dry/wet допускает обе полярности, разница не меньше 200 отсчётов. Индекс ограничен 0..100. Это **индекс по калибровке**, не процент воды в грунте.
5. Шесть последовательных исправных пачек дают качество `ok`; для автополива нужны ещё подтверждения сухого состояния (всего минимум 11 пачек с начала накопления). Возраст показаний проверяется отдельно.
6. После автополива сухое состояние не запускает бесконечные повторы. Повторное срабатывание требует подъёма выше порога на 5 пунктов и последующего высыхания. Порог этого профиля 1..95.
7. Через 120 s после завершения проверяется прирост индекса хотя бы на 3 пункта, если исходный индекс ≤95 и измерение было исправным. Отсутствие отклика или достоверного измерения фиксирует `watering_no_response`. Снять блокировку можно только физически через `ack-fault`, после осмотра. Ручной полив без достоверного почвенного измерения не создаёт такую проверку; остальные защиты действуют.

Пункты 1–7 требуют проверки на разных грунтах и расположениях датчика. Стабильное правдоподобное значение не доказывает исправность: программно нельзя надёжно определить все обрывы, зависший выход или плохой контакт датчика с грунтом. Фильтрация также не определяет стадию роста и цветение.

## Полив и сохранение

- Начальный режим manual, калибровки отсутствуют. Все GPIO по умолчанию не назначены; неопределённый бак и неподготовленный драйвер блокируют насос.
- Бак считается наполненным после трёх чтений подряд. Пусто/неизвестно — немедленно; возраст больше 1500 ms — неизвестно. Контакт должен замыкаться на землю при наличии воды; обрыв провода даёт пусто. Это не диагностирует замыкание провода на землю.
- Команда сохраняется вместе с резервом полной порции, cooldown и событием **до** включения выхода. Повтор UUID возвращает прежний результат; другой объём с прежним UUID — конфликт.
- Stop адресует конкретную команду, выключает насос до записи и не требует часов. Stop, пришедший раньше Water, запрещает поздний запуск того же ID.
- Журнал хранит 128 команд минимум 24 h. Когда свободного места нет, новый полив запрещён; действующий полив можно остановить. Нельзя обходить заполнение очисткой NVS.
- При перезапуске незавершённый полив становится failed; автоматическое возобновление отсутствует. До осмотра действует защёлка ошибки, до синхронизации времени — `clock_unset`.
- Полная порция остаётся в защитном резерве даже после ранней остановки. Резерв снимается только после истечения календарного **и** монотонного окна; после перезапуска отсчитывается минимум 24 h. Cooldown после перезапуска выдерживает как минимум полный настроенный интервал плюс 30 s. Это намеренно консервативный профиль ([ADR-0011](adr/0011-conservative-water-accounting.md)).
- NVS не стирается при ошибке инициализации. `state_v1` — внутренний blob фиксированной версии и размера, **не переносимый сетевой формат**. Изменение C layout требует новой версии и миграции с сохранением лимитов. Не прошивать дамп между разными архитектурами.

Раздел NVS — 128 KiB. Сохраняются настройки, boot epochs, команды и важные события, но не каждое измерение ADC. Полная запись журнала проста для первого стенда, однако ресурс flash при массовых отклонённых запросах ещё не измерен. Радиокоманды ограничены по частоте; вход Stop не задерживается этим ограничением. Перед эксплуатационным релизом нужны нагрузочный тест, оценка износа и отдельный план хранения.

## Сборка и проверки

Установить ESP-IDF v5.3.4 и инструменты для двух targets, выполнить `export.sh` из SDK. SDK не копируется в репозиторий.

```sh
cd firmware/node
idf.py set-target esp32c3
idf.py build
cd ../hub
idf.py set-target esp32s3
idf.py build
```

Чистая сборка берёт `sdkconfig.defaults`. После изменения defaults с уже созданным sdkconfig нужно осознанно пересоздать конфигурацию, иначе старые значения могут иметь приоритет. Файлы sdkconfig и build не коммитятся. OTA в профиле не реализовано: разделы содержат один factory app, не изображают двойной слот обновлений.

Из корня репозитория:

```sh
npm ci
npm run check
cmake -S tests/firmware -B tests/build -DSP_MBEDTLS_SOURCE="$IDF_PATH/components/mbedtls/mbedtls"
cmake --build tests/build
ctest --test-dir tests/build --output-on-failure
python3 tests/firmware/test_provision.py
```

Host-проверки используют ASan/UBSan, включают отказы записи, повторы и перестановку сообщений, перезапуск, лимиты, плохой датчик, насыщение журнала, CBOR и 20 000 повреждённых пакетов. При заданном `SP_MBEDTLS_SOURCE` проверяются тот же AEAD-код, подмена каждого байта кадра, другой ключ и replay epochs. Без него криптографический тест не запускается; CI задаёт путь явно.

## Подготовка двух плат

1. Сначала прошить приложение с **отключённым насосом** командой `idf.py -p PORT flash monitor` в соответствующем проекте. Без provisioning оно выдаёт STA MAC и остаётся заблокированным. Это ещё не назначает выводы.
2. Проверить ревизии, питание и все сигналы. Насосу нужен внешний драйвер, защита индуктивной нагрузки, внешний pulldown и подходящий источник питания. GPIO не питает насос. Выводы USB, flash, загрузочные straps и светодиод не используются профилем. Совместимость разрешённого номера с конкретной платой всё равно нужно проверить.
3. Для **новой стендовой установки** создать ключи. Следующие MAC — только пример; заменить на реальные STA MAC:

```sh
python3 tools/provision.py --hub-mac 02:00:00:00:00:01 \
  --node-mac 02:00:00:00:00:02 --country RU --channel 6 \
  --output secrets/bench-01
```

Без `--pins` аппаратные выходы остаются выключены. После проверки схемы добавить `--pins SOIL,TANK,PUMP` один раз для каждого Node при создании **первоначального** комплекта. Скрипт не перезаписывает существующий каталог и не прошивает платы. Для новой генерации создаются новые ключи всей установки. Для дальнейшей смены GPIO на уже действующей установке нужен отдельный инструмент изменения только provisioning, не восстановление старого дампа NVS.

4. CSV содержат секреты, имеют права 0600 и должны оставаться в игнорируемом каталоге `secrets/`. Конвертировать каждый CSV официальным генератором SDK:

```sh
python "$IDF_PATH/components/nvs_flash/nvs_partition_generator/nvs_partition_gen.py" \
  generate secrets/bench-01/hub.csv secrets/bench-01/hub.nvs.bin 0x20000
```

Повторить для `node-0.csv`. Загрузить **свой** образ NVS на **новую** плату по адресу `0x9000` с esptool SDK. Образ занимает весь раздел и заменяет историю/лимиты/счётчики, поэтому эта операция не является способом обновления прошивки или устранения ошибки. Для существующей установки нельзя восстанавливать старые epochs с теми же ключами. Обычное `idf.py flash` NVS не перезаписывает.

5. После перезапуска открыть monitor Hub и Node. `status` показывает состояние и CBOR; `time <Unix-UTC-ms>` на Hub передаёт время всем настроенным Node. Часы телефона/ПК задаются пользователем; NTP/облако не нужны.

## Инженерная консоль

UUID команды — UUIDv4 в виде 32 строчных hex без дефисов. Создать на компьютере: `python3 -c 'import uuid; print(uuid.uuid4().hex)'`. На повторе запроса использовать тот же UUID.

```text
status
time <UTC-ms>
config <peer> <expected-rev> <dry-ADC> <wet-ADC> <flow-ul/s> <auto-0/1> <threshold> <portion-ml> <daily-ml> <maxrun-s> <interval-min> <maxage-s>
water <peer> <UUID> <ml>
stop <peer> <новый-UUID> <UUID-полива>
query <peer> <UUID>
ack-fault
```

На Hub peer — индекс из manifest (0..9), на Node — 0 для локального устройства. `ack-fault` существует только на USB Node. Команда config задаёт всю управляющую конфигурацию атомарно с проверкой revision; имена растений и каталог не относятся к этой инженерной команде. Производительность насоса задаётся в **мкл/с**, измеряется отдельно на стенде; не копировать чужое значение.

Hub не отправляет Water для offline-устройства. Выполняет до трёх передач с интервалом 1500 ms, UUID и deadline не меняются. `request_outcome_unknown` означает именно неизвестный результат: проверить `query` с исходным ID; новый ID не является безопасным повтором. Ответ running подтверждает запуск, итог нужно запросить отдельно или получить из истории. Console `SPP ... cbor=...` декодируется `python tools/spp_inspect.py HEX`.

## Что должно быть проверено перед настоящим поливом

- Нулевой выход насоса при загрузке, reset, отключении USB, brownout и watchdog; отдельное измерение GPTimer cutoff при занятом application task и записи flash.
- Фактический диапазон датчика и отклик после полива; помехи при старте насоса, отключение/короткое замыкание датчика, пересыхание/переувлажнение грунта.
- Поплавок, пустой бак, разрыв линии и задержка остановки. Механическая защита от сифона и протечек.
- Повтор Water, потеря результата, Stop перед Water, перезапуск обеих плат, потеря питания в процессе NVS commit.
- Радиоканал с десятью зашифрованными пирами, свободная память, число потерянных кадров; будущая совместная работа AP и ESP-NOW проверяется отдельно.
- Автономный режим при выключенном Hub после успешной синхронизации; после reboot без времени запуск должен быть запрещён.

Отдельные незавершённые задачи: полноценный REST, браузерная авторизация, согласование clock-unset результатов Stop с публичной JSON-схемой, метаданные растений, пользовательская привязка/отвязка с сохранением ID, смена ключей, защищённое хранение ключей и обновление прошивки. Не включать эти возможности в список работающих функций.
