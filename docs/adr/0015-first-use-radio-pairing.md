# ADR-0015: поиск и привязка C3 при первом использовании
Статус: Принято
Дата: 2026-11-02

## Контекст

Первый запуск Hub заканчивается домашним Wi-Fi. Добавление растений должно происходить из основного приложения, без паспорта Hub и приватного файла привязки. Для текущего домашнего стенда владелец явно выбрал подключение без QR/PoP. Это осознанное ограничение первой версии, не доказательство подлинности обнаруженной платы. Дополняет ADR-0013; старый USB-assisted путь остаётся для совместимости.

## Решение

Новый C3 устанавливается действием `new-node` мастера. Установка требует пустой NVS; firmware создаёт свою случайную идентичность и PMK один раз, только при отсутствии namespace provision. Существующую идентичность, safety и links не стирают и не «ремонтируют». Непривязанный C3 объявляет себя в течение 120 секунд после запуска, сканируя разрешённые в инженерном профиле каналы 1–11. К домашней сети C3 не подключается. Hub сохраняет канал роутера и открывает поиск только по аутентифицированному действию владельца на 120 секунд. Реестр кандидатов ограничен десятью записями, срок показания кандидата — 12 секунд.

Владелец выбирает конкретный ID. Для первого обмена применяются P-256 ECDH, HKDF-SHA256 и подтверждения HMAC-SHA256 из Mbed TLS. SHA256 всего transcript служит salt HKDF; info — UTF-8 `SmartPlantOS/SPJ1/LMK+APP`. Первые 16 байт результата — LMK, вторые — app key. HMAC app key от `transcript_hash || direction` использует direction 1 для offer и 2 для ACK. Проверяются длины, исходный MAC, ID, nonce, публичная точка и proof. Самостоятельных реализаций эллиптических кривых нет. Индивидуальные LMK/app key не пересылаются по радио. Последующая связь использует существующие ESP-NOW CCMP и SPP AES-GCM/replay epochs.

Это **неаутентифицированный первый обмен ключами**. Активный злоумышленник рядом может подменить первое устройство/перехватить установление доверия. Режим API явно называется first_use_unverified. При первом подключении требуется доверенное окружение. Защищённая от MITM коммерческая привязка требует отдельного PoP/QR/аутентифицированного протокола и ревью; близость устройств и нажатие кнопки сами по себе это не заменяют.

### Радиоформат SPJ1

Все пакеты ограничены 250 байтами ESP-NOW v1. Magic — ASCII SPJ1, следующий байт — тип; поля далее являются byte arrays, а не C struct. Существующий SPP не меняется. Все handshake-пакеты передаются broadcast, чтобы регистрация encrypted peer не мешала завершению обмена. Получатели проверяют адреса, nonce и proof до изменения links. Колбэк Wi-Fi только копирует ограниченный пакет в очередь; криптография/NVS выполняются в application task. Дорогая обработка offer C3 ограничена одним разом в секунду.

- Beacon, type 1, 98 bytes: magic[4], type[1], node_id[6], node_MAC[6], node_nonce[16], node_public[65].
- Offer, type 2, 152 bytes: magic[4], type[1], node_id[6], hub_id[6], hub_MAC[6], node_nonce[16], hub_nonce[16], hub_public[65], proof[32].
- ACK, type 3, 81 bytes: magic[4], type[1], hub_id[6], node_id[6], node_nonce[16], hub_nonce[16], proof[32].

Публичные ключи — SEC1 uncompressed P-256 (0x04 + X + Y), проверяемые Mbed TLS. Transcript = beacon целиком + первые 120 bytes offer без proof. MAC Node присутствует в beacon, MAC Hub — в offer. Генератор случайных чисел — esp_fill_random при включённом Wi-Fi. Приватные скаляры/производные временные буферы очищаются после использования.

### Общий PMK и защищённая доставка

Стенд выявил, что независимо заданные PMK приводят к отсутствию приёма encrypted ESP-NOW, хотя подтверждения первого ECDH-обмена проходят. Используем общий PMK Hub, как в примере Espressif ESP_NOW_Network. Это заменяет допущение ADR-0013 о независимых PMK. Индивидуальные LMK/app key остаются разными для каждого растения.

Дополнительный PMK envelope, type 4, 61 bytes: magic[4], type[1], node_id[6], hub_id[6], nonce[12], ciphertext[16], tag[16]. AES-128-GCM защищает PMK, AAD — первые 17 bytes пакета. Ключ обёртки — HKDF-SHA256(app_key, salt=AAD, info=UTF-8 `SmartPlantOS/SPJ1/PMK`, length=16). Отдельный ключ исключает пересечение GCM-nonce с SPP. Nonce случайный; одна готовая обёртка может повторно передаваться без изменения ciphertext. PMK открытым текстом не передаётся.

Обёртку принимает только привязанный C3 от известного MAC Hub, с правильными ID и GCM tag. PMK сохраняется атомарно в существующем provision/pmk, затем encrypted peer переустанавливается с тем же LMK. При совпадении PMK запись не выполняется. Ошибка применения требует восстановления/перезапуска; links, safety, app key и replay epochs сохраняются. Hub повторяет защищённую обёртку для ещё не подтвердивших SPP-связь peers; после полностью проверенного кадра останавливает её для этого peer. Это позволяет продолжить связь после отключения питания между сохранением links и получением PMK.

### Сохранение и восстановление

C3 сохраняет ожидающие скаляр и nonce как pairing/node_v1 до первой привязки, поэтому выключение до получения offer не меняет транзакцию. Hub перед передачей offer сохраняет pairing/hub_v1 с точным offer и peer, затем существующим атомарным links/registry_v1 добавляет encrypted peer. При перезапуске возобновляется та же транзакция с теми же ключами. Ошибка записи не выдаётся за успех. После получения корректного offer C3 атомарно сохраняет links, прекращает объявления и отправляет proof ACK; повтор offer не заменяет установленную связь. Удаление временного seed не затрагивает safety/replay state.

Hub завершает транзакцию по ACK или первому полностью проверенному SPP-кадру выбранного peer: потерянный ACK и перезапуск C3 после сохранения не должны оставлять рабочую связь в вечном pending. Отказ удаления временного blob может привести к повторному восстановлению той же транзакции после reboot, но не к ротации ключей. По тайм-ауту Hub сохраняет pending и предлагает retry. Автоматического удаления зарезервированного peer и замены ключей нет. API возвращает 202 только как принятие действия, UI отдельно ждёт online.

## Последствия

Один незавершённый handshake на Hub, максимум десять растений. Ключ администратора Hub нужен для действий владельца; ключи C3 вручную вводить не требуется. Новая C3-прошивка нужна для discovery; старые уже привязанные C3 продолжают работу и не становятся доступными для чужого Hub. Для передачи растения другому Hub пока необходим явный USB-сброс с последующей установкой. Автоматический takeover не реализуется.

Текущий поиск показывает аппаратную модель инженерного профиля; доверять заявленной модели как аппаратной аттестации нельзя. Независимый аудит криптопротокола и защита от RF DoS не заявляются. Шифрование flash и Secure Boot в текущем профиле отсутствуют. GPIO/полив не разрешаются фактом привязки, остаются правила Node и необходимость аппаратной настройки.

## Что не проверено

Host-модель и браузерные тесты не заменяют испытания нескольких физических C3, потери питания между каждым NVS commit и сложного RF-окружения. Результаты текущих аппаратных проверок фиксируются отдельно в docs/bench. Без PoP этот профиль не предназначен для среды с активным противником при первой привязке.
