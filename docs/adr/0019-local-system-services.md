# ADR-0019: локальные службы, диагностика и перенос настроек
Статус: Принято
Дата: 2026-11-03

## Контекст

После первичной настройки нужны понятное управление устройствами, диагностика без USB, выбор Wi-Fi, перенос пользовательских метаданных и доступ к приложению с телефона. Отсутствие датчиков не мешает проверять эти сценарии. Физическое выключение C3 приводит к offline; предыдущая запись об offline после OTA не доказывает дефект обновления: владелец сообщил о ручном отключении питания.

## Решение

Службы Hub не переносят защитную логику из Node. GET диагностики возвращает только разрешённые поля: версии, uptime, нормализованную причину перезапуска, состояние сети/радио, счётчики и возраст последнего сообщения. Отчёт не содержит паролей, ключей, SSID, IP, MAC и дампов NVS. Node сообщает отдельное HEALTH-сообщение; сведения старых прошивок остаются неизвестными, а не выдуманными.

Сканирование Wi-Fi запускается явным действием, асинхронно и с ограниченным временем/числом результатов. Во время pairing/обслуживания/OTA оно недоступно. Смена сети сначала проверяется, затем сохраняется; прежняя конфигурация восстанавливается при ошибке. Восстановительная AP включается явным запросом на ограниченное время. Обработчики Wi-Fi только сигнализируют события; JSON, flash и криптография остаются в application task.

Резервная копия версии 1 содержит только UUID растения, имя, комнату и вид. Импорт проходит строгую проверку и предварительный просмотр. Применение требует подтверждения и совпадения SHA-256 снимка текущего каталога, выполняется одним NVS commit. Существующие связи сохраняются; новые растения импортируются без контроллеров. Ни секреты, ни radio binding, ни GPIO, ни калибровка, ни лимиты/счётчики/журнал безопасности не экспортируются и не восстанавливаются. Data ABI остаётся 1.

UI разделяет состояния устройства и датчика, не теряет ввод при фоновых опросах и не повторяет команды после неопределённого ответа. Возобновление загрузки OTA допускается только явным действием с совпадающими UUID, SHA, целью и смещением. Установка на главный экран добавляет manifest и локальные иконки. Offline-кэш и очередь команд не вводятся; приложение требует доступного Hub и не обещает поддержку установки браузером с недоверенным локальным TLS-сертификатом.

Запись результата OTA версии 2 связывает сеанс с адресом раздела, SHA-256 файла и ELF-идентификатором прошивки. Совпадение одного адреса недостаточно: USB может записать другую прошивку в тот же раздел. Откат показывается только при подтверждении состояния кандидата SDK и совпадении его ELF. Старая запись v1 используется только после проверки SHA-256 полного работающего образа; преобразование выполняется в RAM без перезаписи NVS. Неподтверждённая история остаётся неизвестной. RSSI и HEALTH хранятся отдельно от сохраняемых структур pairing; размер peer ABI защищён compile-time проверкой.

В изолированном демо есть управляемые примеры offline, ошибки датчика и обновления. Они не используют API и не затрагивают платы.

## Последствия

У служб есть отдельные контракты и тестируемые границы. Экспорт пригоден для нового Hub, но после восстановления новые растения требуют явной привязки контроллеров. Причины отключения и перезапуска не считаются физическим диагнозом. SSID и адрес доступны на приватной странице сети, но не в диагностическом файле.

## Что не проверено

Host/SDK/browser и аппаратные результаты фиксируются отдельным отчётом. Длительная работа, разные роутеры, реальная установка PWA на iOS/Android и любые исполнительные устройства требуют соответствующего стенда.
