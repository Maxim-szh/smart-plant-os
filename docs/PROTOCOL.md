# Локальный контракт v1

Это спецификация будущего API, а не описание работающей прошивки. Формальная схема — [`spec/v1/schema.json`](../spec/v1/schema.json), примеры — [`spec/v1/examples`](../spec/v1/examples). JSON кодируется UTF-8. Все числа имеют единицы в имени поля или в структуре измерения. `null` означает отсутствие достоверного значения; `0` означает измеренный ноль. Не подменяйте одно другим.

## Идентификаторы и версии

- `schema_version: 1` присутствует в каждом документе. Несовместимое изменение полей требует v2. `api_version` имеет вид `1.0` и возвращается устройством.
- `device_id` создаётся один раз при первом запуске: `spo-` и 12 шестнадцатеричных символов, например `spo-a1b2c3d4e5f6`. Он не зависит от IP, имени, MAC и типа платы. Сброс сетевых настроек не меняет ID.
- `plant_id` — UUID конкретного растения. Переименование и смена вида не меняют его. Новое растение после удаления получает новый ID.
- `command_id` — UUID, создаваемый клиентом до отправки команды. Узел сохраняет ID и принятое решение **до** включения насоса. После перезагрузки незавершённая команда становится `failed`, а повтор с тем же ID не запускает насос. Планируемое окно дедупликации — последние 128 команд и не менее 24 часов; его объём и ресурс записи проверяются до прошивки. После тайм-аута клиент запрашивает результат, а не создаёт новый ID.
- `event_id` имеет вид `<device_id>:<seq>`. `seq` — возрастающий целый номер на узле; после перезагрузки счётчик сохраняется. Если хранение истории переполнилось, номер не используется повторно.

## Время и качество

Календарное время — RFC 3339 UTC с `Z` либо `null`, когда часы не синхронизированы. `uptime_ms` — монотонное время от загрузки; оно сбрасывается при перезагрузке и не заменяет календарную метку. `sample_age_ms` позволяет выявлять старые измерения, пока плата работает. `clock_state` равен `synced` или `unset`.

Качество датчика: `ok`, `stale`, `uncalibrated`, `fault`, `missing`. Индекс почвы `soil_index_pct` — результат калибровки конкретного датчика и субстрата от 0 до 100, **не объёмная доля воды в почве**. Сырой `raw_adc` сохраняется для диагностики. Для бака передаётся `water_present: true|false|null`; процент бака без датчика уровня не выдумывается.

Объём воды без расходомера всегда `estimated_ml`; `measured_ml` появится лишь с измерителем расхода. Запрошенная порция называется `requested_ml`. Интерфейс обязан сохранять это различие.

## HTTP API узла

Префикс `/api/v1`. Ответы: `Content-Type: application/json; charset=utf-8`. Доступ к изменяющим маршрутам требует авторизации, способ привязки будет утверждён до реализации. Размер запросов и частота команд ограничиваются на узле.

| Метод и путь | Ответ | Назначение |
|---|---|---|
| `GET /device` | `Device` | Идентичность, версии, возможности |
| `GET /state` | `State` | Полный снимок одного растения и исполнительного канала |
| `GET /config` | `Config` | Настройки и ревизия; секреты не возвращаются |
| `PUT /config` | `Config` | Замена проверенных настроек с `If-Match: <revision>`; конфликт — `409` |
| `GET /events?after=<seq>&limit=<n>` | `EventPage` | События по порядку; `after` по умолчанию 0, `limit` 1–100, по умолчанию 50 |
| `POST /commands/water` | `CommandResult` | Ручной запрос `{schema_version,command_id,requested_ml}`; `202` при принятии |
| `POST /commands/stop` | `CommandResult` | `{schema_version,command_id,target_command_id}`; `202` при принятии |
| `GET /commands/{command_id}` | `CommandResult` | Проверка результата после тайм-аута/перезагрузки |

`PUT /config` принимает тело `Config` без изменения `device_id`, с новой настройкой и прежней `revision`; заголовок `If-Match` содержит десятичное число этой ревизии. Узел увеличивает ревизию после атомарного сохранения. Недопустимые настройки возвращают `422` с полем, которое не прошло проверку. Пределы значений в схеме описывают формат; прошивка проверяет также жёсткие лимиты конкретного оборудования.

Каждая принятая команда проходит `accepted → running → completed|stopped|failed`; отказ без запуска — `rejected`. Повтор того же `command_id` с тем же телом возвращает прежний результат; с другим телом — `409`. После принятия команды ответ узла содержит `command_id`, поэтому можно опрашивать `/commands/{id}`. `POST /commands/stop` имеет приоритет над обычными запросами; насос должен выключаться независимо от возможности отправить HTTP-ответ.

Коды HTTP: `400` неверный JSON/тип, `401` нет авторизации, `403` нет разрешения, `404` неизвестный ресурс, `409` конфликт ревизии/ID, `410` курсор истории устарел, `422` допустимый JSON с недопустимым значением, `429` слишком много команд, `503` устройство временно не готово. Ошибка имеет `{schema_version, error:{code,message,field?}}`; `message` предназначено для разработчика, UI показывает локализованный текст по `code`.

Для `410 cursor_expired` ответ дополнительно содержит `oldest_seq`; это происходит, когда `after < oldest_seq - 1`. Координатор фиксирует пропуск и продолжает с доступного курсора. `EventPage.next_cursor` — последний возвращённый `seq`, а при пустой странице равен запрошенному `after`. Курсор относится только к указанному `device_id`.

## События и состояния

События v1: `soil.sampled`, `watering.decision`, `watering.started`, `watering.finished`, `fault.raised`, `config.changed`. Типизированный `payload` каждого события описан в схеме. История нужна для проверки решений и восстановления данных после отключения координатора; она не заменяет текущее состояние.

Коды решения/отказа v1: `soil_not_dry`, `sensor_stale`, `sensor_fault`, `sensor_uncalibrated`, `tank_empty`, `tank_unknown`, `pump_uncalibrated`, `cooldown_active`, `daily_limit`, `single_limit`, `pump_busy`, `clock_unset`, `hardware_fault`, `config_invalid`. Значение `ready` означает, что обязательные проверки пройдены, но не обещает будущий полив: состояние может измениться до запуска.

## Совместимость и будущие клиенты

Внутри v1 можно добавлять необязательные поля, но нельзя менять смысл обязательных. Клиент игнорирует незнакомые поля и обрабатывает незнакомый `reason_code` как общий отказ. Новый обязательный датчик или режим требует обновления `capabilities`; клиенты проверяют возможности, а не тип платы.

Координатор предоставляет `GET /api/v1/nodes` с документом `Registry`. Каждый маршрут узла доступен также под `/api/v1/nodes/{device_id}/…` с теми же телами и кодами. Если узел недоступен, координатор возвращает `503 node_offline`; `Registry.online` равен `false`, а `last_seen_at` показывает время последнего успешного опроса. Исторический снимок может храниться в приложении, но должен быть явно обозначен как устаревший.

Координатор и будущий Home Assistant не пишут в GPIO. Они отправляют команды этому API; узел применяет те же ограничения. Для Home Assistant сохраняются стабильные `device_id` и `plant_id`, из которых затем строятся `unique_id` сущностей. NAS/microSD позже получают события по курсору, но не участвуют в решении о поливе.
