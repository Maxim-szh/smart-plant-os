# Безопасность сети: решение до прошивки

Полив — физическое действие. Команды насосу и изменение защитных настроек не могут быть доступны анонимному клиенту локальной сети. Обязательная основа: уникальный секрет/ключ каждого узла, привязка координатора с физическим подтверждением, возможность отозвать привязку, ограничение частоты команд и журнал авторизованных действий. Секреты не возвращаются через `GET /config` и не печатаются в обычном журнале.

Предпочтительное направление — HTTPS API на узле и закрепление сертификата в координаторе при первичной привязке. Полное веб-приложение обслуживает координатор, поэтому браузер не должен обращаться к самоподписанному HTTPS каждого узла напрямую. Первичная настройка Wi-Fi может использовать защищённый механизм ESP-IDF Provisioning, а не собственный протокол без проверки. [Espressif поддерживает HTTPS-сервер на C3](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-reference/protocols/esp_https_server.html) и [защищённый Provisioning Security 2](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-reference/provisioning/protocomm.html).

Это направление ещё требует измерения: в документации Espressif указано около 40 КБ RAM на одно TLS-соединение, что существенно для C3. До реализации API нужно на выбранной C3 проверить память при Wi-Fi, HTTPS, одном клиенте, чтении датчика и активном насосе; затем зафиксировать способ хранения ключа/сертификата, первичной привязки и восстановления доступа. Если HTTPS на конкретной C3 не укладывается в бюджет, потребуется отдельное документированное решение с тем же уровнем контроля доступа. Обычный HTTP с постоянным токеном в локальной сети не считать производственным режимом.

В CI никогда не хранить реальные ключи устройств. Примеры в `spec/v1` содержат только вымышленные идентификаторы и данные.
