# Setup API v1

Локальные операции Hub, отдельные от SPP и `Config` растения. Формальные документы: [schema.json](schema.json); примеры демонстрационные, ключи `11…`/`22…` не используются программой.

Все API требуют HTTPS и текущую Bearer-сессию `/api/v1/session`. Origin и JSON проверяются сервером. Секреты не возвращаются в status/passport. `/setup` и `/setup.js` — публичные статические файлы; сама страница не даёт доступ к настройкам без входа.

| Запрос | Ответ | Поведение |
|---|---|---|
| GET `/api/v1/setup` | 200 Status | сеть, IP, стадия проверки, список ID привязанных C3 |
| GET `/api/v1/setup/passport` | 200 Passport | публичные параметры Hub; не содержит LMK, PMK, app key |
| POST `/api/v1/setup/wifi` | 202 Accepted | WiFiRequest; запуск проверки, не подтверждение подключения |
| POST `/api/v1/setup/peers` | 201 Accepted | Pairing; импорт индивидуальной связи, не подтверждение online |

Дополнительно к JSON Schema SSID проверяется по длине UTF-8 **в байтах**, максимум 32. Пароль — 8–63 печатных ASCII-байта; открытые сети и WPA-Enterprise этим профилем не поддерживаются. Проверка подключения ограничена 30 s; `connecting` запрещает второй запрос настройки. Credentials сохраняются после GOT_IP атомарным `network/home_v1`; прежняя конфигурация применяется при неудаче. После перезагрузки in-flight проверка не возобновляется. Статус не сообщает пароль. При смене канала AP телефон может потерять соединение.

Pairing содержит ровно шесть полей. LMK и app key должны различаться; ключи, уже используемые другой связью Hub, отклоняются. Экранированный NUL в запросе запрещён. `hub_id` должен совпадать с текущей установкой. Повтор MAC/ID, полный реестр или занятая настройка дают 409 `peer_exists_or_full`; повтор не ротирует ключи. Неверный файл даёт 400 `pairing_rejected`. Новая связь добавляется в ограниченный реестр и NVS blob `links/registry_v1`; порядок слотов не меняется, replay epochs сохраняются. Файл создаётся программой только для нового C3 с пустым NVS. После импорта Hub и C3 используют те же LMK/app key; локальные PMK генерируются независимо (PMK защищает локальное хранение LMK, кадры защищаются общим LMK).

Неизвестный исход HTTP не разрешает автоматически повторять mutation: сначала GET Status. Для pairing отказ записи может потребовать проверить статус после перезагрузки. Автоматический откат физического flash-состояния при ошибке NVS не обещается.

Ошибки используют `schema_version:1,error:{code,message}`. Неверный JSON — 400 `invalid_body`, неверные сетевые параметры — 400 `wifi_invalid`, уже запущенная проба — 409 `setup_busy`, прочие маршруты — 404 `not_found`. Ошибки auth/Origin/размера наследуют существующий API. Версия внутреннего NVS blob не является сетевым форматом.
