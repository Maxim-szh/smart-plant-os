# Setup API v1

Локальные операции Hub, отдельные от SPP и `Config` растения. Формальные документы: [schema.json](schema.json); примеры демонстрационные, ключи `11…`/`22…` не используются программой.

Все API требуют HTTPS и текущую сессию (Bearer или HttpOnly-cookie) `/api/v1/session`. Origin и JSON проверяются сервером. Секреты не возвращаются в status/passport. `/setup` и `/setup.js` — публичные статические файлы; сама страница не даёт доступ к настройкам без входа.

| Запрос | Ответ | Поведение |
|---|---|---|
| GET `/api/v1/setup` | 200 Status | сеть, IP, стадия проверки, список ID привязанных C3 |
| GET `/api/v1/setup/passport` | 200 Passport | публичные параметры Hub; не содержит LMK, PMK, app key |
| POST `/api/v1/setup/wifi` | 202 Accepted | WiFiRequest; запуск проверки, не подтверждение подключения |
| POST `/api/v1/setup/peers` | 201 Accepted | Pairing; импорт индивидуальной связи, не подтверждение online |

Дополнительно к JSON Schema SSID проверяется по длине UTF-8 **в байтах**, максимум 32. Пароль — 8–63 печатных ASCII-байта; открытые сети и WPA-Enterprise этим профилем не поддерживаются. Проверка подключения ограничена 30 s; `connecting` запрещает второй запрос настройки. Credentials сохраняются после GOT_IP атомарным `network/home_v1`; прежняя конфигурация применяется при неудаче. После перезагрузки in-flight проверка не возобновляется. Статус не сообщает пароль. При смене канала AP телефон может потерять соединение.

Pairing содержит ровно шесть полей. LMK и app key должны различаться; ключи, уже используемые другой связью Hub, отклоняются. Экранированный NUL в запросе запрещён. `hub_id` должен совпадать с текущей установкой. Повтор MAC/ID, полный реестр или занятая настройка дают 409 `peer_exists_or_full`; повтор не ротирует ключи. Неверный файл даёт 400 `pairing_rejected`. Новая связь добавляется в ограниченный реестр и NVS blob `links/registry_v1`; порядок слотов не меняется, replay epochs сохраняются. Файл создаётся программой только для нового C3 с пустым NVS. После импорта Hub и C3 используют те же LMK/app key. В актуальной прошивке C3 получает общий PMK Hub в отдельной AES-GCM-обёртке с индивидуальным ключом; исходные независимые PMK не обеспечили приём encrypted ESP-NOW на стенде. См. ADR-0015.

Неизвестный исход HTTP не разрешает автоматически повторять mutation: сначала GET Status. Для pairing отказ записи может потребовать проверить статус после перезагрузки. Автоматический откат физического flash-состояния при ошибке NVS не обещается.

Ошибки используют `schema_version:1,error:{code,message}`. Неверный JSON — 400 `invalid_body`, неверные сетевые параметры — 400 `wifi_invalid`, уже запущенная проба — 409 `setup_busy`, прочие маршруты — 404 `not_found`. Ошибки auth/Origin/размера наследуют существующий API. Версия внутреннего NVS blob не является сетевым форматом.

Дополнительное необязательное поле Status `setup_ap_enabled` сообщает фактическое состояние точки настройки. Политика AP — [ADR-0014](../../../docs/adr/0014-setup-ap-lifecycle-and-reset.md): WPA2 `smartplantos`, выключение через 30 s устойчивой связи и восстановление после 60 s её отсутствия. Это не меняет аутентификацию API.

Маршрутизация интерфейса: GET `/` через адрес AP отвечает 303 Location `/setup`; через адрес STA отдаёт приложение растений. GET `/setup` доступен на обоих интерфейсах. UI проходит этапы ключ → Wi-Fi → подтверждение с домашним адресом; переход не считается успешным по одному 202. Схемы API этим не изменяются.

## Поиск C3 из приложения

Все запросы требуют текущую сессию (Bearer или HttpOnly-cookie) владельца и прежние проверки HTTPS/Origin.

| Запрос | Результат |
|---|---|
| GET `/api/v1/setup/pairing` | 200 DiscoveryStatus: фаза, окно, кандидаты, выбранный ID, pending |
| POST `/api/v1/setup/pairing/search` `{}` | 202 Accepted: открыть поиск на 120 s; новый поиск очищает кандидатов |
| POST `/api/v1/setup/pairing/connect` DiscoveryConnect | 202 Accepted: выбрать найденный ID, сохранить транзакцию, начать обмен |
| POST `/api/v1/setup/pairing/retry` `{}` | 202 Accepted: продолжить ту же сохранённую транзакцию с теми же ключами |

Некорректное тело — 400; занятой поиск/связь, отсутствующий кандидат, ошибка записи или недоступный сервис — 409 `pairing_busy_or_unavailable`. 202 не означает, что C3 доступен. `paired` означает подтверждение ключа ACK либо корректным SPP-кадром; признак online берётся отдельно из `/api/v1/nodes`. `waiting_device` сохраняет pending и допускает retry без ротации ключей. Секреты, MAC и публичные ключи handshake не выдаются через JSON. Кандидаты устаревают через 12 s, максимум 10. Потеря ответа не разрешает автоматический повтор POST.

Режим `first_use_unverified` шифрует последующую связь, но не аутентифицирует устройство при первом обмене внешним секретом/кодом. Нельзя описывать его как защищённый от активного MITM. Радиоформат и восстановление — [ADR-0015](../../../docs/adr/0015-first-use-radio-pairing.md).

Сеанс браузера: [ADR-0016](../../../docs/adr/0016-browser-session-cookie.md). Cookie — дополнение к Bearer, JSON-ответ входа совместим. Ключ администратора через status не выдаётся; вход и его ограничения неизменны.
