# Участие в Smart Plant OS

Мы строим полноценную локальную систему ухода за растениями, но реализуем её небольшими проверяемыми этапами. Общий ориентир — [план разработки](docs/ROADMAP.md), [архитектура](docs/ARCHITECTURE.md) и [ADR](docs/adr/README.md). Решение, влияющее на несколько документов или схем, оформляется новым ADR; принятый ADR меняют новым ADR.

## Перед началом работы

1. Выберите задачу из ближайшего этапа плана. Для новой крупной функции сначала откройте issue с пользовательским сценарием, границами функции и влиянием на ESP32-C3.
2. Проверьте [контракт v1](docs/PROTOCOL.md), [правила полива](docs/WATERING.md) и аппаратные допущения. Если нужен новый тип данных, предложите изменение схемы и примера одновременно.
3. Данные в `web/index.html` демонстрационные. Не переносите фиктивные GPIO и диагностические значения в спецификации или прошивку.
4. Не добавляйте зависимость от облака, Hub, Home Assistant, NAS или microSD в обязательный путь безопасности полива. Node должен сохранять автономность по сохранённой конфигурации.

## Контракты и совместимость

- Один Node обслуживает одно растение. Идентификаторы устройства и растения не меняются при переименовании.
- [`spec/v1`](spec/v1) — источник истины для передаваемых полей. Сначала измените документацию и схемы, затем пример, затем реализацию и проверки.
- Не меняйте смысл существующего поля без новой версии контракта. Новые необязательные поля допустимы в пределах v1; удаление, переименование, смена единицы или изменение обязательности требуют v2 и плана миграции.
- Различайте измеренное (`measured`), оценочное (`estimated`) и рекомендацию (`advisory`). У показаний есть единица и качество.
- UI, Hub, ИИ и будущий адаптер Home Assistant не должны включать насос напрямую или обходить ограничения Node.
- Не подменяйте термины: `soil_index_pct` — индекс по калибровке, а не объёмная влажность; объём без расходомера — `estimated_ml`.
- Не публикуйте реальные ключи, секреты привязки и дампы NVS; не записывайте секреты в журналы.

## Порядок изменения

Для изменения поведения опишите сценарий и ожидаемый результат. Для аппаратного изменения приложите схему питания, параметры нагрузки, ревизию платы и результаты измерений. Для UI покажите состояние «нет связи» и отказ команды, если затронуты данные устройства.

В pull request укажите цель, затронутые документы/схемы, результаты проверки и оставшиеся ограничения. Небольшие связанные PR предпочтительнее одного большого. Используйте `Signed-off-by` в коммитах (`git commit -s`). Перед отправкой выполните `npm ci` и `npm run check`.

Прошивка находится в `firmware/`; точные команды проверок и матрица реализации — в [FIRMWARE.md](docs/FIRMWARE.md). Изменения ядра и транспорта требуют host-тестов, включая AEAD, и сборки обеих плат. Ориентир сценариев — [правила полива](docs/WATERING.md). Не утверждайте аппаратную совместимость без проверки конкретного модуля и питания.

Для C-кода используется `.clang-format` (clang-format 18). Новые датчики добавляются через драйвер и качество измерения, интеграции — через сервис команд Hub, новые хранилища — через `sp_history_store_t`. Нельзя переносить GPIO или NVS в обработчик Wi-Fi, обходить проверки ради «ручного режима», менять номера SPP enum или C layout сохранённого `state_v1` без версии и миграции. Изменяя сообщения, обновляйте SPP, векторы, преобразование к публичному контракту и тесты; изменение схемы сопровождайте примером. Телеметрия не должна вызывать запись flash на каждом чтении. Реальные MAC, ключи и дампы в PR не попадают.

В PR отдельно указывайте: что проверено на хосте, какие targets собраны и что проверено на физическом стенде. Для новых защит нужны сценарии отказа, для исправления протокола — повтор/потеря/перезапуск, для изменения формата хранения — восстановление старого состояния без обнуления лимитов. Не считайте всю архитектурную стадию завершённой из-за добавления каркаса или успешной компиляции.

## Где сейчас нужна помощь

- Проверка справочника растений по источникам и отделение советов по уходу от управления насосом.
- Измерение и документирование конкретных ESP32-S3 N16R8 и ESP32-C3 Super Mini, а также ESP-NOW на стенде ([NETWORK.md](docs/NETWORK.md)).
- Ревью JSON-схем, сценариев отказа и авторизации команд.
- Доступность HTML-прототипа и обозначение демонстрационных данных.

До аппаратных испытаний ориентируйтесь на [критерии готовности](docs/ROADMAP.md#готовность-к-прошивке), а не на количество экранов в прототипе.
